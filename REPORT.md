# Search_Tree: исследование четырёх реализаций упорядоченного множества

## 1. Зачем проводилось исследование

В этой работе я сравниваю четыре реализации одной задачи: хранить уникальные ключи, добавлять новые и отвечать на запросы об их положении в отсортированном множестве. Мне важно понять, как устройство контейнера влияет на время работы: где выгоден простой массив, когда полезно сбалансированное дерево и почему готовый std::set не всегда оказывается быстрым для нужной операции.

У классов одинаковый основной интерфейс. Поэтому каждому контейнеру можно передать одни и те же данные и запросы, а различия искать в способе хранения и алгоритмах. Исследование не выбирает «лучшее дерево вообще»: оно сравнивает конкретные реализации на конкретных нагрузках.

### Четыре операции

| Метод | Что делает |
| --- | --- |
| `insert(x)` | Добавляет ключ. Повтор уже существующего ключа не увеличивает множество. |
| `select(i)` | Возвращает i-й ключ в порядке компаратора; нумерация с 1. Неверный индекс даёт `std::nullopt`. |
| `count_less(x)` | Возвращает число ключей строго меньше x. |
| `range_count(l, r)` | Считает ключи в `(l, r]`: левая граница исключена, правая включена. |

В измерениях используются `int` и обычный возрастающий порядок. Произвольный тип ключа и компаратор поддерживаются шаблонами, но их стоимость здесь отдельно не исследуется. Для range_count сделаны два блока: узкий и широкий диапазон. Поэтому на паттерн приходится пять основных измерений на каждый класс.

### Четыре реализации

| Класс | Устройство и важные особенности |
| --- | --- |
| `Sorted_Vector` | Отсортированный `std::vector` уникальных ключей. Позиция вставки и границы находятся бинарным поиском, select обращается по индексу. Вставки внутрь массива требуют сдвигов. |
| `Set_Adapter` | Обёртка над `std::set`. Стандартный контейнер предоставляет упорядоченные итераторы и логарифмический поиск, но не быстрый доступ по рангу. select и подсчёт расстояний используют проход по итераторам. |
| `AVL_Tree` | Собственное сбалансированное бинарное дерево с двусторонней прошивкой, высотами и размерами поддеревьев. В исследуемой новой версии все три запроса используют размеры поддеревьев. Узлами владеет дерево; удаление выполняется итеративно. |
| `B_Tree` | Собственное многопутевое дерево с несколькими ключами в узле. Размеры поддеревьев используются для ранговых запросов, владение детьми выражено через `unique_ptr`. В benchmark минимальная степень **t = 2**, то есть максимум три ключа в узле. |

Наличие прошивки не делает select автоматически быстрым. Прошивка помогает обходить ключи по порядку без стека; для быстрого поиска по номеру нужны размеры поддеревьев.

### Ожидаемая сложность

Обозначим U — число уникальных ключей в заполненном контейнере, K — число ключей запрошенного диапазона. Ниже приведена стоимость одного вызова; для пустых и маленьких контейнеров подразумевается постоянная нижняя граница затрат.

| Класс | insert, худший случай | select | count_less | range_count |
| --- | --- | --- | --- | --- |
| Sorted_Vector | O(U) из-за сдвигов или роста памяти | O(1) | O(log U) | O(log U) |
| Set_Adapter | O(log U) | O(i), до O(U) | O(log U + ранг), до O(U) | O(log U + K) |
| Новый AVL_Tree | O(log U) | O(log U) | O(log U) | O(log U) |
| B_Tree при фиксированном t | O(log U) | O(log U) | O(log U) | O(log U) |

В B-дереве время операции зависит не только от высоты дерева, но и от перебора ключей и детей внутри каждого узла. Число таких проверок в узле имеет порядок t, а высота дерева — порядок logₜ U. Поэтому, если учитывать зависимость от t, сложность составляет O(t · logₜ U). В этой работе t всегда равно 2, поэтому оценка упрощается до O(log U). У вектора есть важные частные случаи: при попытке вставить дубликат сдвиги не нужны, а при добавлении возрастающих уникальных ключей новые элементы попадают в конец. Однако бинарный поиск позиции вставки всё равно выполняется, а при нехватке ёмкости приходится выделять новую память и переносить элементы.

Если контейнер содержит N уникальных ключей, то есть U = N, можно оценить суммарную стоимость N вызовов select — по одному для каждого ранга от 1 до N. У вектора каждый вызов стоит O(1), поэтому все запросы вместе дают O(N). У AVL_Tree и B_Tree с размерами поддеревьев один запрос стоит O(log N), а все вместе — O(N log N). Set_Adapter каждый раз проходит от начала множества до нужной позиции, поэтому суммарная стоимость достигает O(N²). Такой же порядок ожидается для N запросов широкого диапазона в Set_Adapter: каждый запрос требует обхода примерно половины N ключей. Эти оценки следуют из алгоритмов в коде; графики показывают результаты измерений, но сами по себе не доказывают сложность.

## 2. Как получены и отобраны данные

Использованы 20 размеров входа:

`1000, 1300, 1700, 2200, 2900, 3800, 5000, 6500, 8500, 10000, 13000, 17000, 22000, 29000, 38000, 50000, 65000, 80000, 90000, 100000`.

Для каждого паттерна сначала создаётся data. Затем из его копии получается ordered — отсортированный массив уникальных ключей. Каждый контейнер начинает вставки пустым; запросы выполняются после заполнения. Генерация данных, парсинг, печать, проверка размера и уничтожение контейнера в измеряемые блоки не входят. В измерение вставки входят необходимые выделения памяти самого контейнера.

Последовательность запросов устроена так:

1. **insert:** вставить каждый элемент data, включая повторы.
2. **select:** для каждого элемента data заранее вычислить его ранг в ordered и запросить этот ранг. Повторы сохраняются.
3. **count_less:** запросить каждый ключ из data в исходном порядке.
4. **Узкий range_count:** для позиции p ключа в ordered выбрать левую позицию min(p, U−2), затем соседний правый ключ. Диапазон содержит один уникальный ключ. Для последнего ключа повторяется последний допустимый диапазон.
5. **Широкий range_count:** ширина в рангах w = floor(U/2), левая позиция min(p, U−w−1), правая — левая + w. Это половина уникальных ключей, а не половина числовой оси. Из-за ограничения границы часть правых диапазонов повторяется.

При U = 1 оба диапазона задаются как (key, key] и пусты. При U = 5 широкий диапазон содержит два ключа. Таким образом, число запросов одинаково для классов, но запросы не обязаны быть уникальными или равномерно распределёнными по возможным диапазонам.

Таймер — `std::chrono::steady_clock`. На графиках **Y — полное время блока в миллисекундах, X — входной размер N**. Среднее время одного вызова при необходимости получается делением на фактическое число операций. Для Single_element выполняется только один вызов, а N означает значение ключа.

### Версии и окружение

- C++20, Release: `-O3 -DNDEBUG -std=c++20`, GCC 13.3.0.
- Ubuntu в WSL2, Linux 6.6.87.2-microsoft-standard-WSL2; AMD Ryzen 7 5700U, 8 ядер / 16 логических процессоров по сведениям окружения. Закрепление процесса за ядром и фиксация частоты не выполнялись.

### Почему в отчёте используется новая версия AVL

В первой версии select шёл по прошивке от минимального ключа, а range_count обходил элементы диапазона. При N = 90 000 на возрастающих данных они занимали около 88,1 с и 39,1 с для select и широкого range_count соответственно. В B-дереве в это же время использовались размеры поддеревьев — сравнивались разные алгоритмы запросов.

В новом AVL select спускается по размерам левых поддеревьев, а range_count вычисляет разность двух рангов «не больше границы». Старые результаты сохранены для будущего отдельного сравнения до/после, но в основные линии AVL не подмешиваются.

Перемещение контейнера не входит в замеры. У Sorted_Vector и Set_Adapter move-операции генерируются автоматически. Для B_Tree их можно явно объявить `= default`, поскольку объявленный деструктор подавляет автоматическую генерацию; для AVL с владеющим сырым root_ нужна собственная передача владения. Это отдельное улучшение интерфейса, не объяснение времени поиска.

### Границы интерпретации

Каждая точка — **один прогон**, а не среднее по нескольким независимым повторам. Общие длительные запуски проходили с перерывами работы компьютера; полное время жизни процесса нельзя выдавать за непрерывное время вычисления. Влияние возможной паузы внутри конкретного блока отдельно не зафиксировано.

Небольшую разницу во времени мы не считаем устойчивым преимуществом. Данные позволяют увидеть крупные различия алгоритмов и характер роста; точные проценты и причины отдельных скачков потребуют повторов и профилирования.

### 3.1. Строго возрастающая последовательность — `Strictly_increasing`

**Данные:** `1, 2, …, N`. **Размер множества:** `U = N`.

Новые ключи идут в конец отсортированного вектора: сдвигать уже вставленные элементы не нужно. Однако текущая реализация всё равно ищет позицию через lower_bound, а при росте ёмкости возможны перераспределения памяти. Для деревьев это проверка вставок в одну сторону при сохранении балансировки.

| select | 9.7965 | 137145 | 1.23084 | 7.41679 |

| range_count — узкий | 17.339 | 45.8399 | 23.0324 | 12.7915 |
| range_count — широкий | 15.6643 | 243659 | 16.1109 | 13.959 |

- **select:** минимальное время — **Sorted_Vector: 1.23084 мс**, максимальное — **Set_Adapter: 137145 мс**. Sorted_Vector был лучшим на всех 20 размерах.
- **count_less:** минимальное время — **AVL_Tree: 6.34515 мс**, максимальное — **Set_Adapter: 165911 мс**. По всем размерам AVL_Tree и Sorted_Vector разделили лидерство — по 10 побед.

Запрос select у вектора остаётся самым дешёвым: нужен доступ по индексу. В новой версии AVL поиск по рангу уже не обходит все предыдущие ключи. У Set_Adapter такой обход сохранился, как и линейный подсчёт в count_less и широком диапазоне. На последней точке несколько быстрых операций вектора заметно дороже, чем при N = 90 000; смену лидера здесь нельзя объяснять одной сложностью алгоритма.

### 3.2. Строго убывающая последовательность — `Strictly_decreasing`

**Данные:** `N, N−1, …, 1`. **Размер множества:** `U = N`.

| range_count — узкий | Sorted_Vector | Sorted_Vector | AVL_Tree |
| range_count — широкий | AVL_Tree | AVL_Tree | AVL_Tree |

На этих трёх размерах по пяти замерам минимумы распределились так: AVL_Tree — 8, Sorted_Vector — 7. При равных временах минимум засчитывается каждому классу.

Даже линейный обход Set_Adapter здесь короткий: он проходит максимум несколько ключей. Поэтому огромного отставания, видимого на больших уникальных множествах, нет. При фиксированном U общее время должно определяться главным образом числом запросов N. Результаты относятся к маленькому множеству, а не к большому дереву из экстремальных уникальных чисел.

При постоянном U линейная по U операция может быть очень дешёвой. Этот результат не противоречит её плохому масштабированию на уникальных ключах.

### 3.10. Один элемент — `Single_element`

**Данные:** `data = {N}`. **Размер множества:** `U = 1`, `data.size() = 1`.

Здесь параметр N задаёт значение единственного ключа, а не количество элементов. Выполняется одна вставка и по одному запросу каждого вида. select(1) возвращает N, count_less(N) возвращает 0; диапазоны (N, N] пусты.

Общее время при N = 100 000, **мс**:

| Метод | B_Tree | Set_Adapter | Sorted_Vector | Новый AVL_Tree |

| select | 0.000414 | 4.4e-05 | 2.1e-05 | 3.1e-05 |
| count_less | 6.5e-05 | 3.3e-05 | 6.5e-05 | 3.1e-05 |
| range_count — узкий | 3.2e-05 | 5.4e-05 | 4.4e-05 | 5.1e-05 |
| range_count — широкий | 3.3e-05 | 3.2e-05 | 4.4e-05 | 3.1e-05 |

- **insert:** минимальное время — **AVL_Tree: 0.000216 мс**, максимальное — **B_Tree: 0.000457 мс**. Чаще всего минимум был у AVL_Tree — 13 из 20 размеров.
- **select:** минимальное время — **Sorted_Vector: 2.1e-05 мс**, максимальное — **B_Tree: 0.000414 мс**. Чаще всего минимум был у Sorted_Vector — 13 из 20 размеров.
- **count_less:** минимальное время — **AVL_Tree: 3.1e-05 мс**, максимальное — **B_Tree: 6.5e-05 мс**. Чаще всего минимум был у Set_Adapter — 13 из 20 размеров.
- **range_count — узкий:** минимальное время — **B_Tree: 3.2e-05 мс**, максимальное — **Set_Adapter: 5.4e-05 мс**. Чаще всего минимум был у B_Tree — 13 из 20 размеров.
- **range_count — широкий:** минимальное время — **AVL_Tree: 3.1e-05 мс**, максимальное — **Sorted_Vector: 4.4e-05 мс**. Чаще всего минимум был у AVL_Tree — 13 из 20 размеров.

**По всем 20 размерам** число минимальных времён по пяти замерам: AVL_Tree — 42, Sorted_Vector — 33, Set_Adapter — 27, B_Tree — 16. Это подсчёт отдельных результатов, а не оценка полного времени работы программы.

**Последние три размера — N = 80 000, 90 000 и 100 000:**

Этот сценарий нельзя использовать для изучения роста сложности: контейнер всегда состоит из одного элемента. По оси X ниже показан входной параметр N, а не фактическая мощность множества. Однократные операции сопоставимы с накладными расходами таймера, поэтому формального победителя по таким точкам не выбираем.

### 3.11. Минимальный, средний и максимальный ключ: First / Middle / Last

Здесь «средний» означает ключ в середине отсортированного набора, а не среднее время. Контейнер сначала заполняется числами от 1 до N. Затем select и count_less отдельно вызываются для первого, среднего и последнего элемента. Каждый из шести замеров содержит N // 3 повторений одного запроса. Для range_count таких замеров нет.

При N = 100 000 это 33 333 вызова для каждой строки. select получает индексы 1, 50 001 и 100 000; count_less получает ключи с теми же значениями. В таблице — **общее время в миллисекундах**. AVL взят из новой отдельной серии, как и в основных сравнениях.

| Метод и случай | B_Tree | Set_Adapter | Sorted_Vector | Новый AVL_Tree |
| --- | ---: | ---: | ---: | ---: |
| select — First | 1.49843 | 0.02096 | 0.016454 | 0.703609 |
| select — Middle | 1.55439 | 48288.9 | 0.036565 | 1.89262 |
| select — Last | 1.74675 | 130904 | 0.025639 | 2.28293 |
| count_less — First | 1.49906 | 0.634207 | 0.559881 | 0.448017 |
| count_less — Middle | 1.63857 | 48719 | 0.552012 | 1.40793 |
| count_less — Last | 2.19537 | 131537 | 0.742054 | 1.88861 |

**Кто чаще был быстрее на всей серии из 20 размеров** (при равенстве минимума учитываются оба класса, поэтому сумма может быть больше 20):

- **select, First:** Sorted_Vector — 20, Set_Adapter — 1.
- **select, Middle:** Sorted_Vector — 20.
- **select, Last:** Sorted_Vector — 20.
- **count_less, First:** AVL_Tree — 14, Set_Adapter — 6.
- **count_less, Middle:** Sorted_Vector — 14, AVL_Tree — 6.
- **count_less, Last:** Sorted_Vector — 18, AVL_Tree — 2.

**Главное отличие видно у Set_Adapter.** Первый элемент select получает почти сразу, а до среднего и последнего каждый раз идёт от начала. При N = 100 000 серия для среднего элемента заняла около 48,3 с, для последнего — 130,9 с. У count_less похожая ситуация: для минимального ключа расстояние от начала равно нулю, а для среднего и максимального приходится проходить большую часть множества. Эти серии заняли около 48,7 с и 131,5 с. Поэтому утверждение «set медленно ищет любой ключ» неверно: здесь дорого обходится именно подсчёт позиции.

**У Sorted_Vector select не зависит от того, какой индекс мы запросили.** Во всех трёх случаях это доступ к элементу массива. Различия между небольшими временами First, Middle и Last не означают разную сложность. count_less использует бинарный поиск, поэтому и для максимального ключа не приходится проходить весь массив.

**AVL_Tree и B_Tree не обходят все предшествующие элементы.** Они спускаются по дереву и используют размеры поддеревьев. Поэтому запрос максимального ключа не становится линейным. Конкретные пути и время могут различаться: например, на последнем размере B_Tree быстрее нового AVL в select для Middle и Last, но AVL быстрее B_Tree во всех трёх случаях count_less. Это результаты данной серии, а не правило для любых деревьев.

Эти случаи показывают, почему одного запроса к минимуму недостаточно для сравнения: он скрывает дорогой проход Set_Adapter. Повторение одного и того же запроса также отличается от перебора всех ключей: используются одни и те же пути поиска. Поэтому результаты First/Middle/Last рассматриваются отдельно от основных паттернов. Очень маленькие времена включают влияние оптимизации и цикла измерения; по ним нельзя надёжно объявлять преимущество в несколько наносекунд.

## 4. Какой контейнер лучше подходит для разных данных

**Если данные возрастают или почти отсортированы, Sorted_Vector — хороший вариант для заполнения и дальнейших запросов.** Новые ключи обычно добавляются в конец, поэтому сдвигов почти нет. Это относится к Strictly_increasing, Nearly_sorted, возрастающим отрицательным числам и With_duplicates. Вектор не выигрывает каждую вставку: например, на двух из последних трёх размеров Strictly_increasing быстрее заполнялся Set_Adapter. Но у вектора особенно дешёвый select, а count_less и оба диапазона часто оказываются среди самых быстрых. В With_duplicates он показал минимальное время вставки на 18 из 20 размеров.

**Если числа приходят в обратном, случайном или чередующемся порядке, заполнение вектора становится дороже.** В Strictly_decreasing и Alternating_low_high приходится сдвигать много уже сохранённых элементов; при Random вставки тоже часто попадают внутрь массива. Для такого заполнения лучше подходят деревья. Например, Set_Adapter чаще был первым по вставке на убывающих и чередующихся данных. На Random при N = 100 000 деревья показали близкие времена — около 38 мс, а вектор — около 156 мс. После заполнения ситуация меняется: вектор снова быстро отвечает на запросы. Поэтому выбирать нужно с учётом обеих частей работы, а не только insert или только select.

**Новый AVL_Tree подходит, когда нужны и вставки в разном порядке, и частые запросы по позиции или диапазону.** Балансировка сохраняет небольшую высоту, а размеры поддеревьев позволяют пропускать целые ветви. На возрастающем наборе при N = 100 000 AVL оказался самым быстрым для count_less и обоих диапазонов. При этом на убывающих и случайных данных в той же последней точке эти запросы быстрее выполнял вектор. То есть AVL даёт удобное сочетание операций, но не является победителем на каждом паттерне.

**B_Tree также хорошо справляется с запросами по номеру и широкими диапазонами, однако в этой конфигурации не показало общего преимущества перед AVL и вектором.** Например, на With_duplicates при N = 100 000 оно быстрее AVL во всех трёх видах поиска, включая оба диапазона, но медленнее вектора. На Random оно быстрее AVL для широкого диапазона, а на возрастающих данных уступает AVL по всем измеренным операциям. Здесь исследуется конкретное B-дерево со степенью t = 2; по этим результатам нельзя судить о вариантах с другой степенью.

**Set_Adapter хорошо показал себя на вставках, но для частых запросов select, count_less и широкого range_count по большому множеству подходит хуже.** Причина проста: поиск границы быстрый, а подсчёт позиции или числа элементов выполняется проходом по итераторам. В узком диапазоне проход короткий, поэтому большого отставания обычно нет. First/Middle/Last особенно ясно показывают эту разницу: первый элемент получается быстро, а средний и последний требуют длинного обхода.

**Если во входных данных много повторов, важно учитывать, сколько уникальных ключей в итоге хранится.** В All_equal это один ключ: здесь сравнивается работа с дубликатами и одноэлементным множеством. В With_extreme_values ключей пять: AVL чаще был быстрее на вставке, а Sorted_Vector — на select. Дорогие на больших множествах проходы Set_Adapter здесь короткие. Эти результаты нельзя переносить на контейнер из ста тысяч разных ключей. В Single_element каждый метод вызывается всего один раз. Операция выполняется настолько быстро, что время работы самого таймера заметно влияет на результат. Поэтому по этому тесту нельзя надёжно определить, какой контейнер быстрее.

Полученные результаты согласуются с устройством алгоритмов: вектор быстро читает по индексу, но платит за сдвиги при вставках; Set_Adapter платит за последовательный подсчёт; AVL и B-дерево используют размеры поддеревьев, поэтому иногда выигрывают по скокрости. При этом измерения не доказывают сложность и не позволяют обещать точное преимущество в процентах. У нас по одному прогону на каждый размер, поэтому небольшую разницу и отдельные скачки нужно воспринимать осторожно. Для практического выбора главный вопрос — что программа делает чаще: заполняет контейнер, выбирает элементы по номеру или считает ключи в диапазонах.

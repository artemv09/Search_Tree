# Search_Tree: исследование четырёх реализаций упорядоченного множества

## 1. Зачем проводилось исследование

В этой работе я реализовал четыре варианта упорядоченного множества: на основе отсортированного вектора, std::set, AVL-дерева и B-дерева. Затем я сравнил их скорость на разных данных и наборах команд, чтобы понять, какой вариант лучше подходит для конкретных условий: размера и порядка данных, наличия повторов, видов запросов и доли вставок.

Все четыре класса выполняют одинаковые операции и получают одинаковые данные. Я исследую два режима: сначала заполнил контейнер с данными, а затем выполнял запросы (разделы 2–3) или чередовал вставки с запросами в растущем контейнере (раздел 4). Это сравнение конкретных реализаций; результат зависит от порядка ключей, размера множества и состава команд.

### Четыре операции

| Метод | Что делает |
| --- | --- |
| `insert(x)` | Добавляет ключ. Повтор уже существующего ключа не увеличивает множество. |
| `select(i)` | Возвращает i-й ключ в порядке компаратора; нумерация с 1. Неверный индекс даёт `std::nullopt`. |
| `count_less(x)` | Возвращает число ключей строго меньше x. |
| `range_count(l, r)` | Считает ключи в `(l, r]`: левая граница исключена, правая включена. |

Например, в множестве `{2, 5, 9}` вызов `select(2)` вернёт 5, `count_less(9)` — 2, а `range_count(2, 9)` — 2: учитываются ключи 5 и 9. **Рангом здесь называется номер ключа в отсортированном множестве, начиная с 1.**

В измерениях используются `int` и обычный возрастающий порядок. Произвольный тип ключа и компаратор поддерживаются шаблонами, но их стоимость здесь отдельно не исследуется. В первой части для range_count проверяются узкий и широкий диапазоны. Поэтому для каждого паттерна — то есть заданного порядка входных данных — получаются пять отдельных замеров на класс: вставки и четыре серии запросов.

### Четыре реализации

| Класс | Устройство и важные особенности |
| --- | --- |
| `Sorted_Vector` | Отсортированный `std::vector` уникальных ключей. Позиция вставки и границы находятся бинарным поиском, select обращается по индексу. Вставки внутрь массива требуют сдвигов. |
| `Set_Adapter` | Обёртка над `std::set`. Стандартный контейнер предоставляет упорядоченные итераторы и логарифмический поиск, но не быстрый доступ по рангу. select и подсчёт расстояний используют проход по итераторам. |
| `AVL_Tree` | Собственное сбалансированное бинарное дерево с двусторонней прошивкой, высотами и размерами поддеревьев. В исследуемой новой версии все три запроса используют размеры поддеревьев. Узлами владеет дерево; удаление выполняется итеративно. |
| `B_Tree` | Собственное многопутевое дерево с несколькими ключами в узле. Размеры поддеревьев используются для ранговых запросов, владение детьми выражено через `unique_ptr`. В прежнем benchmark минимальная степень **t = 2**, то есть максимум три ключа в узле. |

Прошивка — это ссылки на соседние ключи в отсортированном порядке: они позволяют обходить AVL без стека. Для быстрого select дополнительно нужен размер каждого поддерева, включая его корневой узел: зная это число, поиск может пропускать целые ветви.

### Ожидаемая сложность

Здесь **U — число хранящихся уникальных ключей**, i — индекс, переданный в select, R — число ключей меньше аргумента count_less, K — число ключей внутри запрошенного диапазона. Таблица описывает стоимость **одного вызова**, а не всей серии.

O(1) означает, что число действий не растёт с U; O(log U) — растёт медленно, как высота сбалансированного дерева; O(U) — может расти пропорционально размеру множества. Эти оценки описывают рост работы, но не задают время в миллисекундах.

| Класс | insert, худший случай | select | count_less | range_count |
| --- | --- | --- | --- | --- |
| Sorted_Vector | O(U) из-за сдвигов или роста памяти | O(1) | O(log U) | O(log U) |
| Set_Adapter | O(log U) | O(i), до O(U) | O(log U + R), до O(U) | O(log U + K) |
| Новый AVL_Tree | O(log U) | O(log U) | O(log U) | O(log U) |
| B_Tree при фиксированном t | O(log U) | O(log U) | O(log U) | O(log U) |

Параметр t — минимальная степень B-дерева: узел вмещает не более 2t−1 ключей. Чем больше t, тем шире могут быть узлы. Время операции зависит не только от высоты дерева, но и от перебора ключей и детей внутри каждого узла. Число таких проверок в узле имеет порядок t, а высота дерева — порядок logₜ U. Поэтому, если учитывать зависимость от t, сложность составляет O(t · logₜ U). В прежней серии t = 2; в смешанной серии сравниваются t от 2 до 64. Для каждого фиксированного t оценка по U упрощается до O(log U). У вектора есть важные частные случаи: при попытке вставить дубликат сдвиги не нужны, а при добавлении возрастающих уникальных ключей новые элементы попадают в конец. Однако бинарный поиск позиции вставки всё равно выполняется, а при нехватке ёмкости приходится выделять новую память и переносить элементы.

Если контейнер содержит N уникальных ключей, то есть U = N, можно оценить суммарную стоимость N вызовов select — по одному для каждого ранга от 1 до N. У вектора каждый вызов стоит O(1), поэтому все запросы вместе дают O(N). У AVL_Tree и B_Tree с размерами поддеревьев один запрос стоит O(log N), а все вместе — O(N log N). Set_Adapter каждый раз проходит от начала множества до нужной позиции, поэтому суммарная стоимость достигает O(N²). Такой же порядок ожидается для N запросов широкого диапазона в Set_Adapter: каждый запрос требует обхода примерно половины N ключей. 

## 2. Как получены прежние данные

Использованы 20 размеров входа:

`1000, 1300, 1700, 2200, 2900, 3800, 5000, 6500, 8500, 10000, 13000, 17000, 22000, 29000, 38000, 50000, 65000, 80000, 90000, 100000`.

В этой части **N — число значений во входной последовательности**, включая повторы. Для каждого паттерна создаётся массив `data` из N значений, а из его копии — `ordered`, отсортированный массив без повторов. Например, для `data = {2, 2, 5}` получаем N = 3, `ordered = {2, 5}` и U = 2. Исключение Single_element описано отдельно: там N задаёт значение единственного ключа. Каждый контейнер начинает вставки пустым; запросы выполняются после заполнения. Генерация данных, парсинг, печать, проверка размера и уничтожение контейнера в измеряемые блоки не входят. В измерение вставки входят необходимые выделения памяти самого контейнера.

Пять замеров выполняются отдельно:

1. **insert:** вставить все значения data, включая повторы.
2. **select:** для каждого значения data заранее найти его номер в ordered и запросить ключ с этим номером. Повторяющиеся значения дают повторные запросы.
3. **count_less:** запросить каждый ключ из data в исходном порядке.
4. **Узкий range_count:** взять текущий ключ и следующий за ним в ordered; для последнего ключа повторить последнюю соседнюю пару. Интервал между ними содержит ровно один ключ, поскольку левая граница исключена.
5. **Широкий range_count:** выбрать границы так, чтобы интервал содержал половину уникальных ключей с округлением вниз. Если справа не хватает ключей, сдвинуть обе границы влево; поэтому ближе к концу массива часть диапазонов повторяется.

Ширина диапазона определяется числом ключей, а не разностью их значений. Например, `(2, 100]` содержит только один ключ, если в множестве есть лишь 2 и 100.

При U = 1 оба диапазона задаются как (key, key] и пусты. При U = 5 широкий диапазон содержит два ключа. Таким образом, число запросов одинаково для классов, но запросы не обязаны быть уникальными или равномерно распределёнными по возможным диапазонам.

Таймер — `std::chrono::steady_clock`. На графиках **Y — полное время блока в миллисекундах, X — входной размер N**. Среднее время одного вызова при необходимости получается делением на фактическое число операций. Для Single_element выполняется только один вызов, а N означает значение ключа.

### Версии и окружение

- C++20, Release: `-O3 -DNDEBUG -std=c++20`, GCC 13.3.0.
- Ubuntu в WSL2, Linux 6.6.87.2-microsoft-standard-WSL2; AMD Ryzen 7 5700U, 8 ядер / 16 логических процессоров по сведениям окружения. Закрепление процесса за ядром и фиксация частоты не выполнялись.

### Почему в отчёте используется новая версия AVL

В первой версии select шёл по прошивке от минимального ключа, а range_count обходил элементы диапазона. При N = 90 000 на возрастающих данных они занимали около 88,1 с и 39,1 с для select и широкого range_count соответственно. В B-дереве в это же время использовались размеры поддеревьев — сравнивались разные алгоритмы запросов.

В обновлённом AVL select использует размеры левых поддеревьев, а range_count вычитает число ключей ≤ l из числа ключей ≤ r. Далее «новый AVL» означает именно эту версию. Её результаты используются во всех основных таблицах и графиках; времена прежнего линейного обхода в них не включены.

Копирование и перемещение контейнеров здесь не измеряются; их стоимость не объясняет различия времени запросов.

### Границы интерпретации

Каждая точка — **один прогон**, а не среднее по нескольким независимым повторам. Общие длительные запуски проходили с перерывами работы компьютера; полное время жизни процесса нельзя выдавать за непрерывное время вычисления. Влияние возможной паузы внутри конкретного блока отдельно не зафиксировано.

Небольшую разницу во времени мы не считаем устойчивым преимуществом. Данные позволяют увидеть крупные различия алгоритмов и характер роста; точные проценты и причины отдельных скачков потребуют повторов и профилирования.

Новые ключи идут в конец отсортированного вектора: сдвигать уже вставленные элементы не нужно. Однако текущая реализация всё равно ищет позицию через lower_bound, а при росте ёмкости возможны перераспределения памяти. Для деревьев это проверка вставок в одну сторону при сохранении балансировки.

### 3.11. Минимальный, средний и максимальный ключ: First / Middle / Last

Здесь «средний» означает ключ в середине отсортированного набора, а не среднее время. Контейнер сначала заполняется числами от 1 до N. Затем select и count_less отдельно вызываются для первого, среднего и последнего элемента. Каждый из шести замеров содержит N / 3 вызовов одного и того же запроса с округлением вниз. При N = 100 000 это 33 333 вызова для каждой строки. select получает индексы 1, 50 001 и 100 000; count_less получает ключи с теми же значениями. В таблице — **общее время в миллисекундах**. AVL взят из новой отдельной серии, как и в основных сравнениях.

| select — First | 1.49843 | 0.02096 | 0.016454 | 0.703609 |

## 4. Смешанные вставки и запросы

### 4.1. Что изменилось в эксперименте

В первой части запросы выполнялись только после заполнения. Теперь я начинаю с пустого множества и чередую вставки с запросами. Так можно проверить, окупается ли быстрый поиск в векторе, если между запросами приходится сдвигать элементы для новых вставок.

**Q — общее число команд, P — процент попыток вставки, U — текущее число уникальных ключей.** Например, Q = 10 000 и P = 50% означают 5000 вставок и 5000 запросов; без повторов итоговый U = 5000. Проверяются доли вставок 10, 25, 50, 75, 90 и 100%. В каждом смешанном сценарии используется один из видов запроса: select, count_less, узкий или широкий range_count. Например, строка «insert + select» при P = 50% означает 5000 вставок, перемежающихся с 5000 вызовов select. При 100% выполняются только вставки.

Seed — начальное значение генератора случайных чисел: при одинаковом seed программа воспроизводит ту же нагрузку. Порядок команд перемешан, но первая команда всегда вставляет ключ, чтобы запросы не попадали в пустой контейнер. Ключи вставляются по возрастанию, по убыванию или случайно. select получает допустимый случайный индекс, count_less — случайный уже существующий ключ; диапазоны содержат один ключ или половину текущего множества. При U = 1 диапазон пуст. Все классы получают одинаковые команды; запросы отсутствующих ключей здесь не исследуются.

Google Benchmark измеряет **время всего блока Q команд**, включая выбор нужного метода и суммирование ответов. Эта сумма помогает проверить результат и не даёт компилятору просто удалить вычисления. Генерация данных, проверка ответов, создание пустого контейнера и его уничтожение исключены из замера; выделение памяти внутри insert включено.

  Используется Release-сборка с оптимизациями. Для каждого сценария выполнено семь повторных измерений; внутри каждого, библиотека может несколько раз выполнить весь блок, чтобы набрать минимум 0,05 с времени измеряемой работы. Каждый проход снова начинается с пустого контейнера, а итоговое время нормируется на один блок. 
| Серия | Что проверяет | Конфигураций × 7 повторений |
|---|---|---:|
| pilot | Q = 1000, небольшой объём | 567 × 7 |
| main | Q = 10 000, основные соотношения команд | 567 × 7 |
| scale | Q = 1000, 10 000, 50 000 | 1701 × 7 |
| seeds | Q = 10 000, seed 42, 123, 2026 | 1701 × 7 |
| duplicates | Q = 10 000, каждый ключ вставляется дважды | 567 × 7 |
| refine | Q = 10 000, вставки 30, 35, 40, 45% | 432 × 7 |

Одна конфигурация — это сочетание класса, степени B-дерева, размера нагрузки, доли вставок, порядка ключей, вида запроса и seed. Всего получено **38 745 замеров: 5535 конфигураций по семь повторений**. 

В следующих таблицах указана **медиана времени блока в миллисекундах**: семь результатов упорядочиваются, затем берётся четвёртый. Это менее чувствительно к единичному скачку, чем среднее. Разброс всё же заметен: в main типичное отношение стандартного отклонения к среднему равно 9,3%, максимальное — 42,2%. Это показатель нестабильности времени, а не граница погрешности; небольшую разницу между классами нельзя автоматически считать преимуществом.

| 4 | 1.141 | 1.302 | 1.510 | 1.524 |
| 8 | 0.921 | 1.014 | 1.338 | 1.271 |
| 16 | 0.792 | 0.916 | 1.238 | 1.251 |
| 32 | 0.762 | 0.854 | 1.310 | 1.289 |
| 64 | 0.679 | 0.835 | 1.157 | 1.218 |

Увеличение t с 2 до 64 сокращает время select-блока примерно в 2,6 раза, остальных блоков — в 1,9–2,2 раза. Более широкие узлы уменьшают высоту, но увеличивают работу внутри узла; в проверенном диапазоне степени 16–64 существенно выгоднее t = 2. **Монотонного ускорения и универсально лучшей степени нет:** близкие результаты 32 и 64 перекрываются по разбросу, а t > 64 не исследовалось.

### 4.6. Где вектор перестаёт быть выгодным

Для блока insert + select при Q = 10 000 серия refine даёт отношение времени вектора к B-дереву t = 64. Значение меньше 1 означает меньшую медиану вектора.

| Порядок | 30% | 35% | 40% | 45% |
|---|---:|---:|---:|---:|
| Возрастающий | 0.28 | 0.31 | 0.30 | 0.31 |
| Убывающий | 0.87 | 1.04 | 1.21 | 1.43 |
| Случайный | 0.78 | 0.89 | 0.91 | 0.95 |

При убывающем порядке ключей вектор быстрее выполняет смесь из 3000 вставок и 7000 запросов select: его медианное время составляет 0,87 от времени B-дерева t = 64, то есть на 13% меньше. Если вставок уже 3500, а запросов 6500, время вектора становится на 4% больше, чем у B-дерева. Получается, что в этих замерах преимущество переходит к B-дереву между 30 и 35% вставок. Но разница при 35% слишком мала с учётом разброса измерений, поэтому считать это точной границей нельзя.

При случайном порядке ключей вектор сохраняет меньшее медианное время на всех проверенных долях от 30 до 45% вставок. При 50% вставок времена вектора и B-дерева близки: уверенного преимущества нет ни у одного из них.

Это видно и при смене seed. Для случайного порядка и 50% вставок серия seeds дала следующие времена смеси insert + select:

| Seed | Sorted_Vector, мс | B_Tree t = 64, мс |
|---:|---:|---:|
| 42 | 0.508 | 0.526 |
| 123 | 0.542 | 0.523 |
| 2026 | 0.533 | 0.530 |

Меньшее число оказывается то у одного, то у другого класса, а разница невелика. Поэтому здесь разумнее говорить о близкой скорости, чем объявлять победителя.

Размер нагрузки тоже меняет выбор. В отдельной серии scale при P = 50% и Q = 50 000 получены следующие медианы времени полного блока случайной нагрузки, мс:

| Смешанный блок | Sorted_Vector | AVL_Tree | B_Tree, t=64 | Set_Adapter |
|---|---:|---:|---:|---:|
| insert + select | 9.492 | 8.313 | 3.845 | 2083.827 |
| insert + count_less | 10.399 | 8.000 | 4.596 | 2670.631 |
| insert + узкий range_count | 12.161 | 10.779 | 6.572 | 8.149 |
| insert + широкий range_count | 12.292 | 11.217 | 6.594 | 2046.564 |

Если сравнить две точки **внутри серии scale**, то в смеси insert + select при росте Q с 10 000 до 50 000 вектор замедляется с 0,542 до 9,492 мс, B-дерево t = 64 — с 0,519 до 3,845 мс. Для убывающего порядка при Q = 50 000 это уже 16,576 против 2,296 мс; для возрастающего вектор сохраняет преимущество: 0,512 против 2,129 мс. Рост согласуется со стоимостью сдвигов.

[Графики масштабирования](#mixed-scale).

### 4.7. Повторы ключей и устойчивость результатов

В серии duplicates каждый ключ вставляется дважды. Число попыток вставки прежнее, но при Q = 10 000 и P = 50% итоговый U = 2500 вместо 5000. Для случайного порядка получены такие медианы полного блока:

| Смесь команд | Sorted_Vector, мс | B_Tree t = 64, мс |
|---|---:|---:|
| insert + select | 0.368 | 0.472 |
| insert + count_less | 0.614 | 0.621 |
| insert + узкий range_count | 0.848 | 0.862 |
| insert + широкий range_count | 0.806 | 0.869 |

Вставка дубликата не требует расширять множество или сдвигать элементы вектора. В этой нагрузке у вектора ниже медиана смеси с select; для count_less и узкого диапазона времена двух классов практически равны.

Повторы измерений устраняют необходимость судить по единственной точке, но не делают условия неизменными. Например, один и тот же Random/select при Q = 10 000, P = 50%, seed = 42 дал вектору 0,714 мс в main и 0,542 мс в scale. Это показывает, что условия измерений менялись между сериями, хотя причину отдельно не измеряли. Поэтому сравниваю классы **внутри одной серии** и не приписываю всю разницу между duplicates и main только повторяющимся ключам.

При фиксированном Q увеличение P означает больше вставок, меньше запросов и более крупное итоговое множество. Поэтому, например, уменьшение общего времени при росте P не означает, что отдельная операция ускорилась: изменился состав работы. Найденные границы относятся к этой смеси команд и этому размеру нагрузки.

## 5. Практический вывод

| Нагрузка | Что следует из измерений |
|---|---|
| Возрастающие ключи, включая частые вставки | Вектор выгоден: нет сдвигов накопленных элементов, select стоит O(1). |
| Убывающие или случайные ключи, растущий объём вставок | Стоимость сдвигов делает деревья выгоднее; особенно заметно при Q = 50 000. |
| Частые select, count_less и широкие диапазоны | Использование размеров поддеревьев в AVL и B-дереве выигрывают у длинных проходов в Set_Adapter. |
| Узкие диапазоны или преимущественно вставки | Set_Adapter остаётся разумным вариантом: линейная часть диапазона короткая либо запросов нет. |
| B-дерево | Степень — существенный параметр: прежний результат t = 2 не характеризовал весь класс. |
| Много дубликатов | Нужно учитывать U: меньшее множество снижает цену поиска и сдвигов. |

Прежние замеры показали преимущества вектора после заполнения; смешанные — цену поддержания его порядка. В этой реализации B-дерево с t = 32–64 часто выгоднее на неупорядоченных вставках, AVL сохраняет логарифмические запросы, но не обязательно минимальное время. Выбор определяется порядком ключей, размером множества и долей вставок.
